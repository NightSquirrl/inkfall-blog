# 单点登录(SSO)详细讲解

## 一、什么是单点登录

单点登录(Single Sign-On,SSO)是指在多个应用系统中,用户只需要登录一次,就可以访问所有相互信任的应用系统,不需要重复输入用户名密码。

**核心价值**:

- 提升用户体验(一次登录,处处访问)
- 集中管理用户身份和权限
- 降低多套账号密码带来的安全风险
- 便于统一的登录日志、审计管理

## 二、SSO 要解决的核心问题

1. **身份的统一认证**:多个系统如何确认"这是同一个用户"
2. **状态的跨域共享**:浏览器的 Cookie 是域隔离的,A系统登录状态如何让B、C系统感知到
3. **登录态的传递与验证**:如何安全地把"已登录"这个事实,从认证中心传递给各个业务系统

## 三、常见实现方案

### 方案1:基于 Cookie + Session 的同域/父子域 SSO

**适用场景**​:多个子系统在同一个主域名下,如 `a.example.com`​、`b.example.com`。

**原理**:

- 登录成功后,把 Session ID 写入 Cookie,并将 Cookie 的 `domain`​ 设置为父域 `.example.com`
- 这样所有 `*.example.com` 的子域都能读取到这个 Cookie
- 各个子系统请求时携带该 Cookie,统一到 Session 服务(如 Redis 集群)校验

**局限**:只能解决同一顶级域名下的子域共享,跨完全不同的域名(如 a.com 和 b.com)无法解决。

### 方案2:基于 CAS(Central Authentication Service)的统一认证中心

这是最经典、最主流的跨域 SSO 方案,原理如下:

**核心角色**:

- **SSO Server(认证中心)**  :独立部署,统一管理所有用户的登录状态
- **SSO Client(各业务系统)**  :本身不做登录校验,登录都转发到认证中心

**登录流程**:

1. 用户访问系统A的受保护资源,系统A发现未登录
2. 系统A重定向到 SSO Server,并携带回调地址(如 `?redirect=http://a.com/callback`)
3. 用户在 SSO Server 输入账号密码完成登录
4. SSO Server 生成一个​**一次性令牌(Ticket)**  ,重定向回系统A的回调地址,并附带该 Ticket
5. 系统A拿着 Ticket 去 SSO Server 后台验证(Server 端到 Server 端通信,更安全),验证通过后获取用户信息
6. 系统A为该用户创建本地会话(Local Session),后续该用户在系统A内的请求都用本地会话即可,不用每次都去 SSO Server 验证

**用户访问系统B时**:

1. 系统B同样发现未登录,重定向到 SSO Server
2. 因为浏览器此时已经和 SSO Server 建立了登录态(SSO Server 域下的 Cookie),所以不需要用户重新输入密码
3. SSO Server 直接生成新的 Ticket,重定向回系统B,系统B验证后建立本地会话

**图示流程(文字版)**  :

```
用户 -> 系统A(未登录)-> 重定向到SSO Server
用户 -> SSO Server 登录(账号密码)-> 生成Ticket -> 重定向回系统A
系统A -> 用Ticket向SSO Server验证 -> 验证通过 -> 系统A建立本地Session

用户 -> 系统B(未登录)-> 重定向到SSO Server(此时已有登录态)
SSO Server -> 直接生成新Ticket -> 重定向回系统B
系统B -> 用Ticket验证 -> 建立本地Session
```

### 方案3:基于 Token(JWT)的 SSO

**原理**:

- 用户在认证中心登录后,颁发一个 **JWT(JSON Web Token)**
- JWT 中包含用户身份信息,并使用私钥签名
- 前端把 Token 存在 localStorage 或通过 Cookie 传递,请求各个系统 API 时携带该 Token(通常放在 `Authorization: Bearer <token>` 请求头中)
- 各个系统各自用公钥验证 Token 签名的合法性,不需要每次都回源到认证中心查询,减轻了认证中心压力

**优点**:

- 无状态(Stateless),认证中心不需要存储 Session,天然支持分布式、跨域
- 各系统验证 Token 不需要网络请求(只要拿到公钥),性能更好
- 天然适合前后端分离、微服务架构、移动端 App

**缺点**:

- Token 一旦签发,在到期前很难主动"撤销"(需要额外维护黑名单机制)
- Token 如果存储在 localStorage,存在 XSS 攻击风险(建议结合 HttpOnly Cookie 或做好 XSS 防护)
- Token 通常携带较多信息,体积比 Session ID 大

### 方案4:OAuth2 / OpenID Connect(第三方授权登录)

严格来说 OAuth2 是​**授权协议**​,OpenID Connect(OIDC)是在 OAuth2 基础上扩展出的​**身份认证协议**,常用于"使用微信/GitHub/Google 账号登录"这类第三方登录场景,也可以用来实现企业内部的 SSO。

**核心流程(以授权码模式为例)**  :

1. 用户访问系统A,系统A重定向到认证服务器(如企业统一门户)
2. 用户登录并同意授权
3. 认证服务器重定向回系统A,并携带 `code`(授权码)
4. 系统A后端用 `code`​ + `client_secret`​ 去认证服务器换取 `access_token`​ 和 `id_token`
5. `id_token`(JWT格式)中包含用户身份信息,系统A解析后即可识别用户身份,建立本地会话

## 四、方案对比

|方案|是否跨域|是否有状态|典型场景|
| -----------------| ----------| ---------------| ------------------------------|
|Cookie 父子域共享|仅同顶级域|有状态|同一公司同一域名下的多个子系统|
|CAS 中心化认证|支持任意域|有状态(Session)|企业内部多系统集成|
|JWT Token|支持任意域|无状态|微服务、前后端分离、App|
|OAuth2/OIDC|支持任意域|通常无状态|第三方登录、开放平台|

## 五、需要考虑的关键问题(面试加分项)

1. **单点登出(SLO, Single Logout)**  :用户在一个系统登出后,如何让所有已登录的系统都退出登录?

   - CAS 方案:认证中心通知各系统清除本地 Session(可以是前端轮询检测登录态,也可以是服务端主动推送)
   - Token 方案:比较麻烦,通常需要维护 Token 黑名单或设置较短过期时间 + Refresh Token 机制
2. **Token/Ticket 的安全性**:

   - Ticket 只能使用一次,防止重放攻击
   - Token 需要签名防篡改,建议设置合理的过期时间
   - 传输过程全程使用 HTTPS
3. **Token 续期机制**​:通常搭配 `access_token`​(短期)+ `refresh_token`(长期)的双 Token 机制,access\_token 过期后用 refresh\_token 静默换取新的 access\_token,避免用户频繁重新登录
4. **跨域 Cookie 的问题**​:如果使用 Cookie 传递登录态,需要注意 `SameSite`​、`Secure` 等属性设置,防止 CSRF 攻击
