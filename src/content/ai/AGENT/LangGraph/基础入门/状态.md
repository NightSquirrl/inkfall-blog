官方推荐了三种定义Schema的方式：TypedDict、dataclass、Pydantic

## **TypedDict-字典对象**

```Python
from langgraph.graph import StateGraph, START, END
from typing import TypedDict, Annotated
from operator import add

class OverAllState(TypedDict):
    logs: Annotated[list[str], add]
    cur_id: str

def node_1(state: OverAllState) -> OverAllState:
    pre_id = state["cur_id"]
    return {
        "logs": ["node_1 运行完毕"],
        "cur_id": pre_id + ", node_1"
    }

def node_2(state: OverAllState) -> OverAllState:
    pre_id = state["cur_id"]
    return {
        "logs": ["node_2 运行完毕"],
        "cur_id": pre_id + ", node_2"
    }

builder = StateGraph(state_schema=OverAllState)
builder.add_node("node_1", node_1)
builder.add_node("node_2", node_2)
builder.add_edge(START, "node_1")
builder.add_edge("node_1", "node_2")
builder.add_edge("node_2", END)

graph = builder.compile()

print(graph.invoke({"cur_id": "start"}))
```

### 结果

```Plain
{ "logs": ["node_1 运行完毕", "node_2 运行完毕"], "cur_id": "start, node_1, node_2" }
```

## **Dataclass**

属性调用方式由`['字段名']`​变为`.字段名`。

```Python
from langgraph.graph import StateGraph, START, END
from typing import Annotated
from dataclasses import dataclass
from operator import add

@dataclass
class OverAllState:
    logs: Annotated[list[str], add]
    cur_id: str

def node_1(state: OverAllState) -> OverAllState:
    pre_id = state.cur_id
    return {
        "logs": ["node_1 运行完毕"],
        "cur_id": pre_id + ", node_1"
    }

def node_2(state: OverAllState) -> OverAllState:
    pre_id = state.cur_id
    return {
        "logs": ["node_2 运行完毕"],
        "cur_id": pre_id + ", node_2"
    }

builder = StateGraph(state_schema=OverAllState)
builder.add_node("node_1", node_1)
builder.add_node("node_2", node_2)
builder.add_edge(START, "node_1")
builder.add_edge("node_1", "node_2")
builder.add_edge("node_2", END)

graph = builder.compile()

print(graph.invoke({"cur_id": "start"}))
```

### 结果

```Plain
{ "logs": ["node_1 运行完毕", "node_2 运行完毕"], "cur_id": "start, node_1, node_2" }
```

## 总结

### **TypedDict-推荐使用**

TypedDict将输入字段视为字典的`Key`​，不匹配时抛出`KeyError`异常。

### **dataclass**

dataclass将输入字段视为类的`属性`​，不匹配时抛出`TypeError（类型错误）`异常。

### **Pydantic**

Pydantic对输入字段进行校验，不匹配时抛出`ValidationError`异常。

## State Reducer

State Reducer（状态归约器）是 LangGraph 中用于定义**状态如何更新的核心机制**。简单来说，当一个节点执行完并返回一个状态更新时，Reducer 决定了这个新数据是应该**追加、累加、覆盖**还是以其他方式合并到整个图的状态中。

把它想象成一个“公共黑板”的更新规则：多个节点（学生）都可以在黑板上写字（更新状态），而 Reducer 就是那个“值日生”，决定新写的内容是覆盖旧的、贴在旁边，还是和旧内容累加起来。

### 为什么需要 Reducer？

最典型的场景是**并行节点的状态冲突**。如果你的图中有两个节点并行执行，它们同时尝试修改同一个状态键，图就不知道应该保留谁的更新，会抛出错误。Reducer 就是来解决这个问题的，它提供了一套明确的合并逻辑，让并行更新变得有序和可预测。

另一个常见场景是**消息列表的处理**。在对话系统中，我们通常希望将新的 AI 回复或用户消息**追加**到历史消息列表中，而不是每次都覆盖掉，这时就需要一个能执行“追加”操作的 Reducer。

### 如何定义和使用 Reducer

在 LangGraph 中，通常使用 Python 的 `Annotated` 类型来为状态字段声明 Reducer。

#### 1\. 内置 Reducer：`add_messages`

这是最常用的内置 Reducer，专门用于处理消息列表。它会智能地将新消息追加到现有消息列表的末尾。

```Python
from typing import Annotated, TypedDict
from langchain_core.messages import BaseMessage
from langgraph.graph.message import add_messages

# 定义状态时，用 Annotated 将 add_messages 绑定到 messages 字段
class State(TypedDict):
    messages: Annotated[list[BaseMessage], add_messages]
    # 没有 Annotated 的字段，默认是直接覆盖
    user_name: str
```

使用了 `add_messages`​ 后，节点只需要返回 `{"messages": [新消息]}`​，LangGraph 就会自动把它拼接到现有的 `messages` 列表后面，而不是覆盖。

#### 2\. 使用运算符作为 Reducer：`operator.add`

对于数值累加或列表合并这类简单逻辑，可以直接使用 `operator.add`。

```Python
from typing import Annotated, TypedDict
from operator import add

class State(TypedDict):
    # 每次节点返回 {"numbers": [新数字]}，这个数字列表都会被追加
    numbers: Annotated[list[int], add] 
    # 如果字段是 int，则累加，但需要确保初始值存在
    total: Annotated[int, add] 
```

#### 3\. 自定义 Reducer

如果需要更复杂的逻辑（例如去重、条件合并），可以编写自己的函数。

```Python
from typing import Annotated, TypedDict

def merge_and_deduplicate(left: list, right: list) -> list:
    """合并列表并去重，同时保持顺序"""
    seen = set(left)
    result = list(left)
    for item in right:
        if item not in seen:
            result.append(item)
            seen.add(item)
    return result

class State(TypedDict):
    # 使用自定义函数作为归约器
    unique_items: Annotated[list[str], merge_and_deduplicate]
```

### 关键点总结

|特征|默认行为 \(无 Reducer\)|使用 Reducer|
| ----| ------------------------------------------| --------------------------------------------------|
|**合并方式**|**直接覆盖**|**自定义合并**（追加、累加等）|
|**适用场景**|状态字段每次由单一节点更新，且旧值不再需要|需要保留历史（如消息列表）、处理并行更新、聚合数值|
|**声明方式**|无需声明|使用 `Annotated[类型, reducer函数]`|
|**并发处理**|**不安全**，并行更新会报错|**安全**，Reducer 定义了合并并行更新的规则|

### 核心要点提炼

- **本质**：Reducer 是控制状态如何合并的“规则函数”。
- **默认值**：如果不指定，状态键默认采用“直接覆盖”的更新方式。
- **关键作用**：处理消息追加、并行更新冲突，以及数值累加等场景。
- **定义方式**：在 Python 中通过 `Annotated` 类型为状态字段绑定 Reducer。

在你的学习笔记中，可以把 Reducer 比作“状态更新的策略”。它让你能精确控制 LangGraph 中那个共享的“黑板”上的信息如何被修改，是构建健壮、有状态智能体的关键一环。

## **图节点更新State**

在 LangGraph 中，节点函数通常不需要返回更新后的完整状态，只需要返回本节点对状态的局部更新。

也就是说，节点的返回值可以只包含需要修改的状态字段。

- 对于节点没有返回的字段，LangGraph 会保留其原有状态值；
- 对于节点返回的字段，LangGraph 会根据该字段是否配置了 `Reducer` 来决定如何合并更新值。

  - 如果字段配置了 `Reducer`​，则使用对应的 `Reducer` 函数将旧值和新值合并；
  - 如果字段没有配置 `Reducer`，则按照默认规则使用节点返回的新值覆盖原值。

LangGraph运行时会按照状态字段的`Reducer`函数将其与当前的最新状态合并

## **Overwrite绕过Reducer**

`Overwrite`​ 的作用是：告诉 LangGraph 本次状态更新不走该字段原本定义的 `Reducer`，而是直接用新值覆盖状态中的旧值。

```Python
from langgraph.graph import StateGraph, START, END
from langgraph.types import Overwrite
from typing import TypedDict, Annotated
from operator import add

class OverAllState(TypedDict):
    logs: Annotated[list[str], add]
    id: str

def node_a(state: OverAllState):
    return {
        "logs": ["node_a"],
        "id": "node_a"
    }

def node_b(state: OverAllState):
    return {
        "logs": Overwrite(["node_b"]),
        "id": "node_b"
    }

def node_c(state: OverAllState):
    return {
        "logs": ["node_c"],
        "id": "node_c"
    }

builder = StateGraph(state_schema=OverAllState)
builder.add_node("node_a", node_a)
builder.add_node("node_b", node_b)
builder.add_node("node_c", node_c)
builder.add_edge(START, "node_a")
builder.add_edge("node_a", "node_b")
builder.add_edge("node_b", "node_c")
builder.add_edge("node_c", END)

graph = builder.compile()
result = graph.invoke({"logs": ["START"], "id": "start"})
print('=' * 30, '-> result <-', '=' * 30)
print(result)
```

## **Multi Schema用法**

在构建复杂智能体时，如果只用单一状态 `State`，会导致两个主要问题：

1. 输入污染：调用方可以传入任意字段，破坏图内部逻辑。
2. 输出冗余：返回值会包含大量调用方不关心的内部字段（如中间推理步骤、token消耗等）[-1](https://lwmzz.blog.csdn.net/article/details/163022561)​[-2](https://notebooks.githubusercontent.com/view/ipynb?browser=chrome&bypass_fastly=true&color_mode=auto&commit=eb22db82a0c974e25b2e52a56940a9e2a5e7911b&device=unknown_device&docs_host=https://docs.github.com&enc_url=68747470733a2f2f7261772e67697468756275736572636f6e74656e742e636f6d2f73686976616d6167722f6c616e67636861696e2d61636164656d792f656232326462383261306339373465323562326535326135363934306139653261356537393131622f6d6f64756c652d322f6d756c7469706c652d736368656d61732e6970796e62&logged_in=false&nwo=shivamagr/langchain-academy&path=module-2/multiple-schemas.ipynb&platform=mac&repository_id=864036292&repository_type=Repository&version=119#e7afcbac-0f39-4500-91f4-2b2a1afc6fb4)。

Multi Schema 提供了清晰的解法，通过定义三个不同的状态“角色”来解耦[-4](https://lwmzz.blog.csdn.net/article/details/163086448)。

节点函数应明确声明入参状态类型和返回状态类型 节点函数的第一个参数通常是当前节点可读取的状态。通过类型注解声明该参数，可以明确表达该节点需要读取哪些字段。 同时，给节点函数声明返回状态类型，也可以帮助阅读者理解该节点会更新哪些字段

### 实战用法：三种典型场景

#### 1\. 场景一：控制对外接口（输入/输出过滤）

这是最核心的用法，能隐藏内部逻辑，暴露干净的API。关键在于 `OverallState`​ 必须是 `InputState`​ 和 `OutputState`​ 的**超集**（包含后两者的所有字段），否则编译会报错。

```Python
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class InputState(TypedDict):
    question: str  # 外部只需传入问题

class OutputState(TypedDict):
    answer: str    # 外部只关心答案

class OverallState(InputState, OutputState):
    # 内部私有字段：既不是输入也不是输出，只在节点间传递
    thinking_steps: list[str]
    token_cost: int

def thinking_node(state: OverallState):
    steps = ["解析问题", "检索知识", "生成答案"]
    # 同时返回输出字段和私有字段
    return {
        "answer": f"关于 '{state['question']}' 的答案是 42",
        "thinking_steps": steps,
        "token_cost": 128
    }

# 组装图，分别指定输入、输出和全局状态
builder = StateGraph(
    OverallState,
    input_schema=InputState,
    output_schema=OutputState
)
builder.add_node("think", thinking_node)
builder.add_edge(START, "think")
builder.add_edge("think", END)
graph = builder.compile()

# 调用时只需传入 question
result = graph.invoke({"question": "生命的意义？"})
print(result)  # 输出: {'answer': "关于 '生命的意义？' 的答案是 42"}
# thinking_steps 和 token_cost 被自动过滤，外部完全不可见 
```

#### 2\. 场景二：节点间传递私有状态（Private State）

在某些场景下，你可能希望某些数据**只在一个或几个节点间传递**，而不被其他节点访问，甚至连 `OverallState` 都不想污染。

```Python
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class OverallState(TypedDict):
    foo: int

class PrivateState(TypedDict):
    # 这个字段只会在 node_1 和 node_2 之间传递
    baz: int

def node_1(state: OverallState):
    # node_1 读取全局状态，返回一个私有状态更新
    print("---Node 1---")
    return {"baz": state['foo'] + 1}

def node_2(state: PrivateState):
    # node_2 只接收私有状态，但返回全局状态更新
    print("---Node 2---")
    return {"foo": state['baz'] + 1}

# 图的 state_schema 仍然是 OverallState
builder = StateGraph(OverallState)
builder.add_node("node_1", node_1)
builder.add_node("node_2", node_2)
builder.add_edge(START, "node_1")
builder.add_edge("node_1", "node_2")
builder.add_edge("node_2", END)
graph = builder.compile()

# 私有字段 baz 不会出现在最终输出中
result = graph.invoke({"foo": 1})
print(result)  # 输出: {'foo': 3} 
```

#### 3\. 场景三：子图（Subgraph）的不同状态模式

当父图和子图状态结构完全不同时，你需要在父图节点中手动进行**状态转换**。

```Python
# 子图有自己的独立状态
class SubGraphState(TypedDict):
    text: str
    summary: str

# 父图状态
class ParentState(TypedDict):
    input_text: str
    result: str

# 在父图节点中调用子图
def call_subgraph(state: ParentState):
    # 1. 将父状态转换为子图状态
    sub_input = {"text": state["input_text"], "summary": ""}
    # 2. 调用子图
    sub_output = sub_graph.invoke(sub_input)
    # 3. 将子图输出转换回父状态
    return {"result": sub_output["summary"]}
```

这种模式在构建多智能体系统时非常常见，每个子图可以作为一个独立的“微服务”运行。

## 预定义状态

### MessagesState

在 LangGraph 中，计算图通常会与 LLM 配合使用。由于 LLM 的多轮交互通常需要维护一组消息记录，LangGraph 官方提供了一个预定义的状态类型：`langgraph.graph.message.MessagesState`，用于简化这类场景下的状态定义。

开发者可以直接继承 \`MessagesState\`，并在此基础上扩展自定义状态字段。

```python
class MessagesState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
```

由此可知，`MessagesState`​ 只有一个字段：`messages`。

该字段的类型是列表，元素类型为 `AnyMessage`​；同时，它通过 `Annotated`​ 绑定了内置 `Reducer`​ 函数 `add_messages`。

`add_messages`​ 的完全限定名（英文全称 `fully qualified name`）是：

案例如下:

```python
from langchain_deepseek import ChatDeepSeek
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import MessagesState
from langchain.messages import HumanMessage

from dotenv import load_dotenv
load_dotenv(override=True)

model = ChatDeepSeek(
    model='deepseek-v4-flash',
    extra_body={
        "thinking": {
            "type": "disabled"
        }
    }
)

class OverAllState(MessagesState):
    username: str
    output: str

def node_a(state: OverAllState) -> OverAllState:
    return {
        "messages": [HumanMessage("你好，我是 " + state["username"])]
    }

def llm_node(state: OverAllState) -> OverAllState:
    res = model.invoke(state["messages"])

    return {
        "messages": [res],
        "output": res.content
    }

builder = StateGraph(state_schema=OverAllState)
builder.add_node("node_a", node_a)
builder.add_node("llm_node", llm_node)
builder.add_edge(START, "node_a")
builder.add_edge("node_a", "llm_node")
builder.add_edge("llm_node", END)

graph = builder.compile()
response = graph.invoke({"username": "小黄"})
print(response)
```

### AgentState

`AgentState`​ 是 `LangChain Agent`​ 内部使用的状态类型。由于 `LangChain Agent`​ 底层也是基于 `LangGraph`​ 运行图构建的，所以从技术上讲，开发者也可以将 `AgentState`​ 或其子类作为自定义 `LangGraph` 的状态类型。

`AgentState`​ 的全类名，也可以称为类的完全限定名（英文全称： `fully qualified class name`​）是：`langchain.agents.middleware.types.AgentState`

源码如下

```python
class AgentState(TypedDict, Generic[ResponseT]):
    """State schema for the agent."""

    messages: Required[Annotated[list[AnyMessage], add_messages]]
    jump_to: NotRequired[Annotated[JumpTo | None, EphemeralValue, PrivateStateAttr]]
    structured_response: NotRequired[Annotated[ResponseT, OmitFromInput]]
```

该状态中主要包含三个字段。

1. messages

```notranslate
messages: Required[Annotated[list[AnyMessage], add_messages]]
```

`messages` 用于存储 Agent 运行过程中的消息列表。

该字段和 `MessagesState`​ 中的 `messages`​ 字段类似，也使用 `add_messages`​ 作为 `Reducer`。

2. jump\_to

```notranslate
jump_to: NotRequired[Annotated[JumpTo | None, EphemeralValue, PrivateStateAttr]]
```

`jump_to`​ 是 `LangChain Agent` 内部使用的控制字段，主要服务于 Agent 中间件体系。

它通常用于表示运行流程的跳转意图，例如某些中间件希望影响 Agent 后续应该进入哪个节点。

需要注意的是，`jump_to` 并不是普通 LangGraph 状态图中的通用跳转机制。

在自定义 `StateGraph`​ 中，即使状态中定义了 `jump_to`​ 字段，`LangGraph`​ 也不会因为该字段的值自动跳转到某个节点。普通 `LangGraph` 运行图如果需要控制后续流向，通常应使用：

```python
Command(goto="node_name")
```

3. structured\_response

```python
structured_response: NotRequired[Annotated[ResponseT, OmitFromInput]]
```

`structured_response` 用于存储 Agent 最终生成的结构化输出。

当使用 `LangChain Agent`​ 的结构化输出能力时，例如指定 `response_format`，Agent 最终生成的结构化结果通常会被写入该字段。

其中，`OmitFromInput` 表示该字段不应作为外部输入字段暴露给调用方，而是由 Agent 运行过程中内部生成。

总体来看，`AgentState` 是专门为 LangChain Agent 运行时设计的状态类型。

因此，在普通自定义 `LangGraph`​ 项目中，一般不建议直接基于 `AgentState` 扩展图状态。
